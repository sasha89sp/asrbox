# AGENTS.md — Правила разработки `asrbox`

Этот документ задаёт обязательные инженерные ограничения для всех участников и ИИ-агентов, работающих с репозиторием `asrbox`.

## 1. Обработка ошибок: запрет `unwrap()` и `expect()`

- Использование `.unwrap()`, `.expect()`, `unwrap_err()`, `expect_err()` **запрещено** во всём workspace, включая утилиту `xtask` и модульные тесты.
- Ограничение закреплено на уровне манифеста `[workspace.lints.clippy]` (`unwrap_used = "deny"`, `expect_used = "deny"`) и проверяется в CI через `cargo clippy --workspace -- -D warnings`.
- Все сбои должны возвращаться через `Result<T, E>` с осмысленным типом ошибки и обрабатываться явно (`?`, `match`, `if let`, `unwrap_or_else`, `ok_or_else`).

## 2. Изоляция `unsafe`: только `crates/platform-windows`

- Во всех крейтах workspace, кроме `crates/platform-windows`, действует `#![forbid(unsafe_code)]` (через `[workspace.lints.rust] unsafe_code = "forbid"`).
- Любой `unsafe`-код и прямые FFI-вызовы WinAPI допускаются **исключительно** внутри `crates/platform-windows`.
- Каждый блок `unsafe` в `crates/platform-windows` обязан сопровождаться комментарием `// SAFETY: ...`, объясняющим проверяемые инварианты указателей, времени жизни, потокобезопасности и кодов возврата Windows API.

## 3. Архитектурные границы модулей

- Прикладные модули `crates/mod-*` (`mod-keyboard`, `mod-dock`, `mod-speech`, `mod-webdav`, `mod-monitor`, `mod-screenshot`, `mod-huawei`) имеют право зависеть **только** от:
  - `crates/core`
  - `crates/platform-api`
  - утверждённых внешних крейтов (с фиксацией выбора в `DECISIONS.md`).
- Запрещено:
  - добавлять прямые зависимости между крейтами `crates/mod-*`;
  - зависеть из `crates/mod-*`, `crates/core` или `crates/platform-api` от `crates/platform-windows` или `crates/app`.
- Связывание конкретной реализации ОС (`crates/platform-windows`) с модулями (`crates/mod-*`) выполняется исключительно в composition root — `crates/app`.

## 4. Честность по CI и среде исполнения

- Код пишется в редакторе без локальной компиляции Windows-таргета; единственная достоверная проверка сборки и тестов выполняется в GitHub Actions на раннере `windows-latest` (`.github/workflows/ci.yml`).
- Запрещено утверждать, что код «скомпилировался», «прошёл тесты» или «проверен clippy», если прогон GitHub Actions для данного коммита фактически не завершён.
- При передаче изменений всегда явно указывать: **«требуется прогон CI на `windows-latest`»** и перечислять ожидаемые шаги проверки.

## 5. Формат вывода кода без заглушек

- Любой создаваемый или изменяемый файл выдаётся **полностью**, готовым к компиляции и прохождению `cargo fmt --check` и `cargo clippy --workspace -- -D warnings`.
- Категорически запрещены:
  - заглушки `todo!()`, `unimplemented!()`, `panic!("not implemented")`;
  - усечения вроде `// ... остальной код`, `/* TODO: заполнить */`, `...`;
  - псевдокод вместо рабочего Rust-кода.
- Исключение — осознанно пустые каркасные точки входа (`src/lib.rs`, `fn main() {}`), явно оговорённые спецификацией версии `0.0.1`.

## 6. Протокол закрытия задачи (Closing Protocol)

Перед завершением любой задачи агент обязан последовательно выполнить все пункты:

1. **Карты и Атлас**:
   - при добавлении/переименовании/удалении крейта обновить `ATLAS.md`;
   - при добавлении/переименовании/удалении любого `.rs`-файла обновить `MAP.md` соответствующего крейта;
   - убедиться, что `cargo run -p xtask -- atlas-check` пройдёт без ошибок.
2. **Инварианты кода**:
   - перепроверить отсутствие `.unwrap()` / `.expect()`;
   - перепроверить отсутствие `unsafe` вне `crates/platform-windows`;
   - перепроверить соблюдение границ зависимостей `mod-*` -> только `core` и `platform-api`;
   - перепроверить форматирование под `rustfmt` (отступы 4 пробела, длина строк <= 100, отсортированные `use`, финальный перевод строки).
3. **Сопроводительная документация**:
   - обновить `HANDOFF.yaml` (актуальная версия, статус, следующий шаг, статус CI);
   - внести запись в `CHANGELOG.md`;
   - при принятии архитектурного решения добавить ADR в `DECISIONS.md`;
   - при обнаружении или исправлении дефекта обновить `BUGS.md`;
   - при изменении требований или бюджетов синхронизировать `SPEC.md`.
4. **Отчётность**:
   - перечислить все созданные и изменённые пути;
   - честно зафиксировать статус CI (`pending_remote_ci` до фактического зелёного прогона в GitHub Actions).
